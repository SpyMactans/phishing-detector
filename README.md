# Hybrid Phishing URL Detector (C++ heuristics + local Random Forest)

A URL risk-assessment tool. The original C++ rule engine is unchanged; a small
local Python service adds a Random Forest trained on labelled URLs. The two
are reported side by side and combined into a final **risk level**
(LOW / MEDIUM / HIGH). It never says a URL is definitely malicious.

```
                C++ program (cpp/main.cpp)
                          |
          +---------------+----------------+
          |                                |
   Heuristic engine                 POST {"url": "..."}
   (your existing rules)            to 127.0.0.1:5050
          |                                |
          |                      Python service (ml/server.py)
          |                       features.py -> Random Forest
          |                                |
   score + findings              {"prediction", "probability", "band", ...}
          |                                |
          +---------------+----------------+
                          |
                 Final risk (table below)
```

## Setup and run

You need Python 3.9+ and a C++17 compiler (g++ or clang++).

```bash
# 1. Python packages (a virtual environment is optional but tidy)
cd ml
python3 -m venv .venv && source .venv/bin/activate      # Windows: py -m venv .venv ; .venv\Scripts\activate
pip install -r requirements.txt

# 2. Build the dataset (downloads ~100 MB of public lists, writes dataset.csv)
python build_dataset.py

# 3. Train. Prints accuracy, precision, recall, F1, confusion matrix. Writes model.pkl
python train.py

# 4. Start the service (leave this terminal open)
python server.py
```

In a second terminal:

```bash
# 5. Compile the C++ program
cd cpp
g++ -std=c++17 -O2 -o detector main.cpp               # Linux / macOS / WSL
#   Windows (MinGW):  g++ -std=c++17 -O2 -o detector.exe main.cpp -lws2_32
#   Windows (MSVC):   cl /EHsc /std:c++17 main.cpp

# 6. Run it
./detector "http://paypa1-login.xyz/verify"            # one or more URLs
./detector                                             # interactive prompt
./detector --no-ml "https://example.com"               # your original output, no AI
```

If the service is not running, the program still works: it prints
`AI Prediction: UNAVAILABLE` and falls back to the heuristics alone.

You can also talk to the service directly:

```bash
curl -s -X POST http://127.0.0.1:5050/predict -H "Content-Type: application/json" \
     -d '{"url": "http://paypa1-login.xyz/verify"}'
```

## How C++ and Python communicate

Plain HTTP over the loopback interface, no libraries on the C++ side:

1. C++ opens a TCP socket to `127.0.0.1:5050` and sends
   `POST /predict` with the body `{"url": "<the URL>"}` (quotes and backslashes in the URL are escaped).
2. Flask replies with JSON:
   ```json
   {"prediction": "phishing", "probability": 0.89, "phishing_probability": 0.89,
    "band": "phish", "top_signals": ["hyphens_in_host = 2", "url_length = 61"]}
   ```
   - `prediction`: `phishing` if P(phishing) >= 0.5, else `legitimate`
   - `probability`: the model's confidence in *that* prediction (what is printed as "AI Confidence")
   - `phishing_probability`: P(phishing) itself
   - `band`: `legit` / `unsure` / `phish` (see "Confidence bands")
   - `top_signals`: up to 3 features that pushed the score towards phishing
3. C++ pulls the fields out of the reply with small `find()` helpers (the reply is flat and simple enough that no JSON library is needed), with a 5-second timeout.

The service listens on `127.0.0.1` only, so other machines cannot reach it. It
treats the URL purely as text and never visits it.

## Why the Python side extracts the features

Two options: C++ computes the features and sends numbers, or C++ sends the raw
URL and Python computes them. This project uses the second, because:

- **No training/serving skew.** `train.py` and `server.py` import the same
  `features.py`, so the model is trained on exactly the numbers it later
  receives. With C++ extraction, you would also have to run the C++ over the whole
  dataset to train, and keep the C++ and Python feature order identical forever.
- **The C++ stays small.** It sends one string and reads one reply.
- **The two engines stay independent.** The heuristic engine and the model look
  at the URL separately, so agreement between them means something.

The cost is that URL parsing exists twice. `features.py` mirrors your
`parseUrl()` on purpose.

## What was reused from your C++ analyzer

| Your C++ code | Use in the ML part |
|---|---|
| `parseUrl()` (scheme, host, port, path, query) | Ported to `parse_url()`. Every feature starts from it |
| `countChar()` on host: dots, hyphens | `dots_in_host`, `hyphens_in_host` |
| `rawUrl.size()` | `url_length` (measured without `http://` and `www.`) |
| `isIPv4()` | `host_is_ip` |
| `hasAt` | `has_at_sign` |
| non-standard port check | `nonstandard_port` |
| `%` count | `percent_count` |
| `//` in path | `double_slash_in_path` |
| Extra measurements in the same spirit | host/path/query length, path depth, query parameters, digits in host |
| Keyword / TLD / shortener / popular-domain lists, `levenshtein()` | **Not model inputs.** They stay in the C++ rules (see below) |
| Weights and verdicts (`+25`, `LIKELY PHISHING`) | **Not model inputs.** They are your opinion, not data |

Why the lists are not given to the model: the public datasets contain almost no
legitimate URLs with words like `login`, so a model trained with a "contains
login" feature learns "login = phishing" and flags real login pages. An early
version did exactly that (`github.com/login` scored 95% phishing). The rule
lists also already feed the heuristic score, and counting the same evidence in
both engines would double-count it.

## How the final risk is decided

Averaging `heuristic_score / 100` with the ML probability would be arbitrary
and statistically unsound:

- The heuristic score is a sum of hand-picked weights, not a probability.
- The ML probability comes from a model trained on a dataset where roughly 30%
  of URLs are phishing. Real traffic is nearly all legitimate, so a "94%"
  is not a real-world probability. Nobody can justify a 50/50 weighting.

Instead, each engine reports a coarse level and a small table combines them:

- Heuristic level uses your existing thresholds: below 20 = safe, 20-49 = suspicious, 50+ = phishing.
- ML level is the band from the model (below).

| Heuristic \ AI band | `legit` | `unsure` | `phish` |
|---|---|---|---|
| LIKELY SAFE (<20) | LOW | MEDIUM | MEDIUM |
| SUSPICIOUS (20-49) | LOW | MEDIUM | HIGH |
| LIKELY PHISHING (50+) | MEDIUM | HIGH | HIGH |

The reasoning behind each cell:

- **Agreement strengthens**: both safe is LOW, both leaning phishing is HIGH.
- **The AI can clear moderate rule hits.** Heuristic "suspicious" plus a confident `legit` band is LOW. This is what stops legitimate sites from being flagged just for containing `login` or a `.xyz` domain.
- **The AI cannot erase strong rule hits.** Strong heuristics plus `legit` is MEDIUM (disagreement, review it).
- **Rules cannot certify safety.** Rules only detect known bad patterns, and finding none is not proof of safety, so "no rule fired" with an unsure model stays MEDIUM.
- **Disagreement or doubt is reported as MEDIUM**, never hidden.

This is a policy, and it is deliberately simple to read. The statistically
principled upgrade is *stacking*: train a small logistic regression on a
labelled validation set with inputs (heuristic score, ML probability), so the
data decides the weights. That needs the heuristic score for every dataset URL, so it is left as future work.

## Confidence bands

`train.py` does not guess cut-offs. On the validation set it picks:

- `phish` band: the lowest score from which at least 90% of URLs are really phishing,
- `legit` band: the highest score up to which at least 95% of URLs are really legitimate.

Everything between is `unsure`. The cut-offs are saved inside `model.pkl`, and
the test set then verifies them on data that was not used to choose them.

## Evaluating the model

`train.py` prints these for the held-out test set:

| Metric | Meaning |
|---|---|
| Accuracy | Share of all URLs classified correctly. Misleading with imbalance: always answering "legitimate" already scores ~70% |
| Precision | Of the URLs flagged phishing, how many really were. Low precision = many false alarms |
| Recall | Of the real phishing URLs, how many were caught. Low recall = missed phishing |
| F1 | Single number balancing precision and recall |
| Confusion matrix | Counts of true/false positives and negatives. Shows *which* mistakes are made |
| ROC-AUC | How well the score ranks phishing above legitimate (0.5 coin flip, 1.0 perfect) |

Results from one run on the test set (about 14,000 URLs from websites never seen in training):

```
Accuracy 0.791   Precision 0.631   Recall 0.738   F1 0.680   ROC-AUC 0.856

                    pred legit   pred phishing
  truly legit             8034            1833
  truly phishing          1116            3138

band     URLs   share truly phishing
legit    3528     5.7%
unsure   8695    26.8%
phish    1898    90.7%
```

These numbers are modest, and that is expected: the model sees only the URL
text. Your numbers will differ a little, because the phishing list changes daily.

**Do not compare these to papers reporting 99%.** Those usually come from
random splits (the same site in train and test) and datasets where the two
classes differ in obvious ways. Both inflate the score without making the model better.

## Leakage and class imbalance: what the code does

Data leakage means information from the test data (or from the label) leaks into training.

- **Duplicates removed** (ignoring `http/https`, case, trailing `/`), and URLs labelled both ways are dropped.
- **Split by website.** Phishing campaigns put many URLs on one site, so a random split would test on sites the model has already seen. `GroupShuffleSplit` keeps every URL of a site on one side. `train.py` asserts that train, validation, and test share no site.
- **Three parts**: train fits the model, validation picks the confidence bands, test is touched only for the final report.
- **No label-derived features**, and your heuristic score is not a model input.
- **Dataset quirks neutralised**: lengths ignore `http://` and `www.` (datasets differ in whether they keep them), `https` is not a feature (nearly all phishing sites use HTTPS today), and `build_dataset.py` caps URLs per site so one site cannot dominate a class.
- **Demo sites removed.** The domains used in the examples below are deleted from the dataset, so the examples are tested on sites the model has not seen.

Class imbalance (about 30% phishing here):

- `class_weight="balanced_subsample"` makes errors on the rarer class cost more.
- Judge the model by precision, recall, F1 and the confusion matrix, not accuracy alone.
- Remember the base rate: in real traffic phishing is far rarer than 30%, so real-world precision would be lower than the table above.

## Limitations

- URL text alone is a weak signal. Real systems also use page content, domain age, certificates, and reputation feeds.
- The public data is not representative: legitimate and phishing URLs were collected separately, at different times, and the "legitimate" pages come from an older dataset. Some legitimate rows in `build_dataset.py` are constructed (a top-1M domain plus a path like `/login`) to stop the model from treating short paths as phishing. Constructed rows mean the model's score on that kind of URL is not independent evidence.
- Your typosquatting rule compares the whole host with `paypal.com`, so `paypa1-login.xyz` (a long host) is not caught by it. Comparing only the first label (`paypa1-login`) with the brand would fix that.
- The model is a risk estimator. Treat "HIGH" as "investigate", never as proof.

## Security notes

- `model.pkl` is a pickle file, which can execute code when loaded. Only load a model you trained yourself.
- The service binds to `127.0.0.1` and validates its input (JSON object, `url` string, max 2048 characters).
- No URL is ever fetched. When testing with real phishing URLs, keep them as text.

## Data sources

`build_dataset.py` downloads: the Phishing.Database "ACTIVE" list

(`zer0h/top-1000000-domains`). Check each repository's licence before redistributing the data.

## One change to your existing code

`parseUrl()` looked for `@` in the whole URL, so `https://medium.com/@user` was parsed as
host `user` and received the +25 "@ trick" penalty. It now looks only in the host part
(before the first `/`, `?` or `#`). Real tricks such as `http://mybank.com@evil.tk/` are still caught.
